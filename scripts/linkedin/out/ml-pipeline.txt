Everyone posts the model. Nobody posts the three weeks of data cleaning. That is where the real engineering lives.

An ML project is a pipeline, and the model is one stage: 1) collect raw data, 2) clean it (missing values, duplicates, outliers, inconsistent types), 3) engineer features (date → day-of-week, text → embeddings, categories → codes), 4) split into train/validation/test, 5) train and tune, 6) evaluate on the untouched test set, 7) deploy, monitor, and retrain as data drifts.

The most common failure is leakage: information from the test set sneaking into training. Scaling the full dataset before splitting, or encoding categories with test-set values, inflates scores in the notebook and collapses in production. Always split first, then transform.

Second failure: optimizing the wrong metric. Accuracy is meaningless on imbalanced data — if 99% of transactions are legit, a model that always says 'legit' scores 99%. For fraud, track precision/recall/F1; for rankings, NDCG; for forecasting, MAE/RMSE. Pick the metric that matches the business cost of being wrong.

Key takeaway: A model is 5% of an ML project. Data quality is 80%.

Tip: Before writing any model code, write the evaluation: what does a wrong prediction cost, and what metric captures it? Everything else follows from that.
